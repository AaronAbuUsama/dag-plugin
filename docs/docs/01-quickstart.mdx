## Install

### Claude Code

```text
/plugin marketplace add AaronAbuUsama/dag-plugin
/plugin install dag@dag-engineering
```

To iterate on a working copy instead, launch with `claude --plugin-dir /path/to/dag-plugin`.

### Codex

```bash
codex plugin marketplace add AaronAbuUsama/dag-plugin
codex plugin add dag@dag-engineering
```

The skill names are shared; only the invocation syntax changes:

| Move | Claude Code | Codex |
| --- | --- | --- |
| Configure | `/dag:setup` | `$dag:setup` |
| Plan | `/dag:plan` | `$dag:plan` |
| Execute | `/dag:execute` | `$dag:execute` |

The remaining examples use the Claude Code spelling for readability; in Codex, replace the leading
slash with `$`.

## Updating Claude Code

New versions do **not** arrive on their own. Claude Code auto-updates Anthropic's own marketplaces by
default and leaves third-party ones — this one included — switched off, so an install stays on whatever
version it was added at until you refresh it.

```bash
claude plugin marketplace update dag-engineering   # pull new commits from the repo
claude plugin update dag@dag-engineering           # move the install to the new version
```

Then **restart Claude Code**. The CLI says so itself — *"restart required to apply"* — because the running
session keeps the version it loaded at launch.

:::warning
**`claude plugin update` defaults to `--scope user`.** If you installed into a single project, a bare
update fails with *"Plugin 'dag' is not installed at scope user"* even though it plainly is installed.
Pass the scope it was installed at:

```bash
claude plugin update dag@dag-engineering --scope local
```

`claude plugin list` shows which scope you have.
:::

To stop doing this by hand, turn auto-update on for the marketplace: run `/plugin`, open the
**Marketplaces** tab, select `dag-engineering`, and choose **Enable auto-update**. Claude Code then
refreshes in the background shortly after each session starts.

### Checking what you're on

```bash
claude plugin list
```

Installs are cached per version at `~/.claude/plugins/cache/dag-engineering/dag/<version>/`, so an old
version stays on disk beside the new one — seeing `0.4.0` there does not mean you are running it.

## Updating Codex

```bash
codex plugin marketplace upgrade dag-engineering
```

Restart the active Codex task after upgrading so it reloads the skill package.

## What it needs

GitHub is the tracker and that is not optional — the chart's **edges** are GitHub's own
issue-dependency relation, which no other tracker renders.

| Requirement | Why |
| --- | --- |
| **`gh`, authenticated** | Non-negotiable. The suite creates issues, sub-issues, dependency links, and labels through it. |
| **Native multi-agent support** | Claude Code uses Agent Teams; Codex uses native child agents. Execution stops before dispatch if the host runner is unavailable. |
| **A browser, `ffmpeg`** | Only what a node's evidence form calls for — driving a UI, pulling a still out of a journey video. |

## Configure the repo, once

```
/dag:setup
```

**What it will do to your repo**, so none of it is a surprise:

- **Opens two throwaway issues**, links one as blocked by the other, reads the relation back, then
  deletes the link and closes both. It refuses to assume GitHub's dependency relation works here — it
  proves it. Two issue numbers get used up.
- **Creates six labels** (below).
- **Writes `CONTEXT.md` and `docs/adr/`** at your repo root, if they don't exist.
- **Writes the shared `## DAG suite` block once in `AGENTS.md`.** Claude Code reaches that canonical
  file through a `CLAUDE.md` symlink where possible, or an `@AGENTS.md` import where the repository
  already has Claude-specific instructions. It shows you the migration diff first.

Re-run it only to change the label set or the doc layout.

| Label | Goes on | Meaning |
| --- | --- | --- |
| `dag:map` | the map issue | The parent issue indexing this chart's nodes. |
| `dag:preflighted` | the map issue | Pre-flight is signed; the DAG is cleared for `/dag:execute`. |
| `dag:halted` | the map issue | Execution stopped this DAG; it is re-planned before it is re-signed. |
| `dag:needs-grilling` | a **de-fog** node | A decision is still open. |
| `dag:needs-research` | a **de-fog** node | A fact must be found first. |
| `dag:needs-prototype` | a **de-fog** node | Not knowable on paper; a spike answers it. |

The three `dag:needs-*` labels go on the de-fog node, never on the build node it blocks — that's the
node `/dag:plan` can actually see. A build node with no de-fog node blocking it is **clear**.

## Plan

```
/dag:plan
```

With no chart yet it says so, then opens `/dag:grill` in the same turn. From then on, every run gives you
one sentence about where you are and performs the next planning move instead of handing you another
command to type.

**You should see** something of this shape:

> No `dag:map` issue on this repo, so there's no chart yet. You're at the start.
> **Next move: grill.** I’ll interview you until the plan is settled, then chart it as issues.

If instead it can't find the labels, `/dag:setup` didn't finish — re-run it.

A typical sequence, one move per turn:

<Steps>
  <Step title="/dag:grill">
    A batched, code-grounded interview. Every question arrives with the problem in real code, what it
    touches, the options as concrete diffs, and a graded recommendation — then the ask.
  </Step>
  <Step title="/dag:prototype or /dag:research">
    Only where the plan needs them: a throwaway spike for what isn't knowable on paper, a background
    agent for a fact that is knowable but not yet known.
  </Step>
  <Step title="/dag:chart">
    Lays the settled plan onto GitHub — a map issue indexing node issues, joined by real blocking edges,
    each node carrying its acceptance criteria **and its proof contract**.
  </Step>
  <Step title="/dag:preflight">
    The gate. Every node checked against its invariants, its criteria, its edges, and a runnable proof
    contract. Signing it adds `dag:preflighted` to the map.
  </Step>
</Steps>

## Execute

```
/dag:execute
```

It checks the signature first and refuses to dispatch without it. Then the main orchestrator walks the
graph wave by wave: it reads the ready set from GitHub, creates one worktree per node and assigns exactly
one node to each teammate. Claude Code uses Agent Teams only; Codex uses native child agents only.
Workers do not self-claim from the host's task list and do not spawn more workers.

**You should see** the ready set named before anything is dispatched, then one PR appear per node. If it
stops immediately saying the DAG isn't signed, pre-flight hasn't run — go back to `/dag:plan`.

Per node it works the **merge gate** — CI green, an independent review whose verdict is posted to the
PR, your own cold read of the diff, and (wherever the branch can run the code) the node's proof
contract satisfied with the evidence in the PR. Findings feed the **escalation ladder**; a bug-class
recurring twice stops the patching and calls `/dag:diagnose`.

:::warning
**`/dag:execute` merges to your base branch and closes the issues, on its own.** That is the point of
the signature — once pre-flight is signed you are not in the loop per node, and it merges each node once
every gate signal is clean. Run it on a branch you are willing to have written to, and read the run
profile on your map (concurrency, models, autonomy) before you start.
:::

You do not step back in per node. `/dag:execute` owns the loop until the graph is done or it hits a hard
stop — and a hard stop arrives pre-validated, with the root cause named and an assessment of whether
fixing it unblocks anything. When it stops, it swaps `dag:preflighted` on the map for `dag:halted`, so the
DAG is back in planning, freezes further dispatch, checks whether any in-flight nodes remain independent,
and prevents a fresh window from resuming execution over the halted graph. `/dag:plan` re-plans the chart
rather than re-signing it with the method that failed.
