**You need to know two of these.** `dag:plan` and `dag:execute` are the doors; everything else is a step
one of them reaches when it is time. Claude Code invokes them as `/dag:*`; Codex invokes them as
`$dag:*`. The full list is here for reference, not as a reading list.

## The doors

| Command | What it does |
| --- | --- |
| `/dag:plan` | The planning door. Reads the chart's state, runs the next move in the same turn, ends at the pre-flight signature. |
| `/dag:execute` | The execution door. Refuses to start without the signature, then walks the signed graph to done-clean. |

## Setup

| Command | What it does |
| --- | --- |
| `/dag:setup` | Once per repo. Confirms GitHub blocking works *on this repo*, creates the label vocabulary, lays out domain docs. |

## Planning

| Command | What it does |
| --- | --- |
| Wayfinding *(internal)* | `dag:plan` resolves destination fog into one Atlas indexing related expedition charts. It is not directly invoked. |
| `/dag:grill` | A batched, code-grounded interview — the whole frontier per round, every question shown in real code with graded options. Never abstract. |
| `/dag:grill-deep` | `grill` plus a durable paper trail: resolved terms to the glossary, hard trade-offs to ADRs, captured as they settle. |
| `/dag:research` | Settles a fact a decision is waiting on, against primary sources, through an assigned research teammate. |
| `/dag:prototype` | The throwaway spike that de-risks a node which isn't knowable on paper. |
| `/dag:chart` | Lays the settled plan onto GitHub — nodes, real blocking edges, readiness labels, and each node's proof contract. |
| `/dag:preflight` | The gate. Every node validated against its invariants, criteria, edges, and a runnable proof contract — every tier command baselined by running it. Signing it opens the execution door. |
| `/dag:replan` | Classifies a returned chart as node-, method-, or destination-wrong and routes it to the level that owns the failure. |

## Execution

| Command | What it does |
| --- | --- |
| `/dag:prove` | Runs a node's proof contract, captures the evidence its surface calls for, commits a receipt, posts the tier table into the PR. |
| `/dag:diagnose` | The nest-finder — one design gap behind a recurring cluster, and the consolidating fix that closes it. |

## Support

| Command | What it does |
| --- | --- |
| `/dag:feedback` | Captures a reproducible, redacted workflow failure and returns it to the plugin source repository. |

## Which ones fire on their own

Most skills are **user-invoked**. Five are **model-invoked**, because another skill or a reported
failure has to be able to reach them:

<CardGroup cols={2}>
  <Card title="research">
    The main planning orchestrator assigns one research teammate per research node, through Agent Teams
    in Claude Code or native child agents in Codex. Each posts its finding back to its own issue and
    cannot self-claim another node.
  </Card>
  <Card title="prototype">
    Model-invoked so a de-fog move can reach it, but in practice `/dag:plan` hands it to **you** — a
    spike is something you drive and judge, not something that resolves in the background.
  </Card>
  <Card title="prove · diagnose">
    `execute` reaches these on its own — `prove` at the merge gate, `diagnose` when the ladder climbs to
    rung 2.
  </Card>
  <Card title="feedback">
    Captures a confirmed or suspected DAG workflow failure with redacted evidence and returns it to the
    plugin source repository.
  </Card>
</CardGroup>

:::note
This is why planning has a router. `dag:plan` reads the next skill and performs that move in the same
turn, preserving one entry point without turning the planning phase into an unattended autopilot.
:::
